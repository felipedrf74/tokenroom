# Tokenroom for iPhone and Apple Watch

The Mac collects; everything else reads. Macs relay readings through the user's private CloudKit database. The iPhone adds providers it reads with its own API keys. The Watch reads iCloud directly. There is no Tokenroom server. Mac rules (providers, tokens, the menu bar) are in `.grok/skills/tokenroom-macos/SKILL.md`.

## Targets and folders

| Target | Bundle ID | Compiles |
|---|---|---|
| TokenroomMobile (iOS 26) | `app.tokenroom.ios` | `TokenroomMobile/`, Shared Core, Relay, UI, APIKeys, Widgets |
| TokenroomWidgets | `…ios.widgets` | `TokenroomWidgets/`, Shared Core, Relay, UI, APIKeys, Widgets |
| TokenroomWatch (watchOS 26) | `…ios.watchkitapp` | `TokenroomWatch/`, Shared Core, Relay, UI |
| TokenroomWatchWidgets | `…ios.watchkitapp.widgets` | `TokenroomWatchWidgets/`, Shared Core, Relay, UI |
| TokenroomMobileTests | `…ios.tests` | `TokenroomMobileTests/`, hosted in the app |

Folders are Xcode synchronized groups: a new file in a folder joins every target that uses the folder. `Shared/Widgets` is iPhone-only (app and widgets). The Watch never compiles `Shared/APIKeys`: no keys on the Watch. Widgets and both Watch targets build with `TOKENROOM_RELAY_READONLY`, which leaves `CloudRelay`'s write methods out. The app embeds the widgets (Embed Foundation Extensions) and the Watch app (Embed Watch Content, `$(CONTENTS_FOLDER_PATH)/Watch`). The Watch app embeds its complications.

Settings live in `Config/*.xcconfig` (`Mobile`, `Widgets`, `Watch`, `WatchWidgets`); never add build settings or `DEVELOPMENT_TEAM` to `project.pbxproj`. Info.plist values that must be filled in by the build (`TokenroomCloudContainer`, `TokenroomAppGroup`, `TokenroomKeychainGroup`) are read through `RelayAvailability` and `AppGroup`, which return nil when a build left them empty. A build without a container (no team) runs without iCloud: the iPhone says "This build can't use iCloud" and still reads keys and offers sample data, and the Watch shows sample data. (The plan had such a build show only sample data.)

`./scripts/typecheck-shared.sh` checks Shared for macOS, iOS, and watchOS (`Shared/Widgets` for iOS only). Run it after touching Shared.

## Data

- **Relay** (`Shared/Relay/CloudRelay.swift`), zone `Tokenroom`: `Source` (one per collector, one writer each), `History` (`hist-<source>`), `Event` (alerts, with `alertKey`; an alert the iPhone shows itself is first claimed with `claimAlert`, created only if no device has, under `UsageAlert.shownKey` so no subscription sends it back), `Prefs` (`prefs-alerts`, the alert choices, written by the iPhone and Macs through `AlertPreferencesSync`: each device keeps the copy it last knew matched iCloud and lays its own changes over the newest shared copy, field by field and threshold level by level, so neither undoes the other; fields a newer Tokenroom added are kept. A copy sent is dated no earlier than the ones it builds on. The iPhone shares one round at a time, and a change made while one goes out follows in the next, laid over what went out; it skips the choices in a zone read that began before its last share reached iCloud (`preferencesSharedAt`), which may hold the copy from before, and doesn't adopt while a share is going out. The fetched record retains its change tag and is saved with `ifServerRecordUnchanged`; conflicts re-read and re-merge the original local delta for at most three attempts, then leave edits pending. Older writers can still overwrite changes). Macs only create alert records (`saveAlert`); an existing one, a claim included, is left as it is. The iPhone, and Macs while sync is on, delete alert records older than two weeks, in batches of at most 400. Envelope windows may carry `pace` (the Mac's measured run-out, which `Pace.evaluate(measured:)` prefers) and providers a `category`. `RelayErrorPolicy` maps CloudKit errors for the Mac and the iPhone alike. Records hold readings only: never tokens, keys, emails, names, account or organization IDs, or paths. `MobileLogicTests.testNoKeyMaterialReachesAnyRecord` guards this. Payloads are plain fields, not `encryptedValues`, by choice: they hold nothing beyond usage numbers, provider and plan names, and reset times; encrypted fields are lost if the account's encryption keys are reset and can't be queried; and with Advanced Data Protection on, the private database is end-to-end encrypted anyway. Moving to encrypted fields later means a new field and a `minReader` bump.
- **Merging**: `RelayMerge` picks each provider's reading (live beats stale, then newest). `ReadingAssembler` adds each collector's history and ranks by urgency (`UsageRanking`: limit reached, running out, most used; balances last). The app, iPhone widgets, the Watch, and complications all go through it.
- **iPhone as a collector**: providers read with keys on the iPhone are relayed as its own `Source` (`kind` `iphone`), with `RelayPublishPolicy`'s send rules. Each of the iPhone's providers shows its newest reading: this launch's, or its own iCloud record's or the App Group cache's (widgets write there too), up to a week old, so a silent-push launch (which doesn't read keys) or a provider resting between calls never drops out, reads "loading", or goes back in time; a key that stopped working shows as that, and when this launch's check failed (offline, busy, rate limited) after the stand-in's reading was taken, the stand-in takes that failure's state, so it's faded and not relayed as live (one a widget took after the failure shows as it is). Until a launch has read iCloud, the saved cache's readings from other devices stand in too (`ReadingCache.carriedSources`, as in widgets), so a launch that can't reach it doesn't show only this iPhone's; signed out of iCloud (`.noAccount`) counts as an empty read, and the next account starts afresh (choices base, subscriptions, publish state). Every iCloud call in a refresh answers within 20 seconds (`MobileStore.iCloud`, over `TimeLimit`), so one that never answers can't hold that refresh, or the ones queued behind it. Budgets and references apply when readings are shown, so changing one shows at once, on saved readings too: a limit that's a budget is marked (`QuotaAmount.isBudget`), and `RelayProvider.applyingBudget` measures it again. The list of providers with keys is saved (`keyedProviders`), and the iPhone doesn't publish until the launch has read its keys; saving or removing a key publishes on that refresh and clears its spacing and 429 wait (`KeyFetchGate.reset`; each value is a defaults key of its own, so one provider's never overwrites another's, though the same provider's is last-writer-wins and checking then recording isn't atomic across the app and widgets). Coming back to the app (and launching it) refreshes a minute after the last refresh that read keys, stamped when a refresh starts and taken back if it's cut short (a silent push in between doesn't count); a refresh asked for during another, forced or due, gets one more pass after it, in a task of its own, so a push's deadline doesn't cut it short. A silent push refreshes readings only (no keys, subscriptions, or pruning), answers within 25 seconds whatever iCloud does (`TimeLimit`, which then cancels it), and tells iOS whether anything changed; background refresh asks for the next one first. Quiet hours take this iPhone's time zone only when that zone changes (`followedTimeZone`), so two iPhones in different zones don't take turns rewriting it. `MobileAppDelegate` owns `MobileStore` and `NewsStore`, so background launches have them. Keys stay in the Keychain group `TEAMID.app.tokenroom.shared`, `AfterFirstUnlockThisDeviceOnly`, never synchronized.
- **Cache**: `ReadingCache` (`readings.json`) in the App Group. The app rewrites it on each rebuild but reloads widgets and hands it to the Watch (WatchConnectivity) only when its `materialHash` changes (amounts count as shown, cents for money; run-outs don't count: `RelayPublishPolicy` sends one once it moves an hour from the one last sent, widgets don't draw them, and the Watch, which does, is handed a run-out that moved an hour too). From the background, where reloads count against WidgetKit's budget, it reloads widgets only for what matters (`ReadingCache.reloadSignature`: a provider added or gone, its state, a level crossed at 80%, 95%, or used up, a window starting over), measured from the saved cache at launch; a reload held back goes out when the app comes forward (anything but `.background` counts as forward). The Watch reloads complications the same way. Sample caches never go to the Watch, and when this launch hasn't sent any readings the Watch link hands over the saved ones. The Watch merges the newest reading individually for each incoming provider (`ReadingCache.mergingUpdate`), honors incoming removals, and rejects delayed whole caches. Confirmed iCloud sign-out empties account caches and reloads complications; phone handovers require account validation and cannot replay a cache saved before sign-out. Connection failures remain visible alongside retained readings, with Retry/Refresh.
- **Widgets and complications** read the cache; when it's over 15 minutes old they read iCloud (and the iPhone's keys, on iPhone) for at most 6 seconds. They never write to iCloud. Widgets due together share one refresh per process (`WidgetRefresher`). `KeyFetchGate` (App Group) shares key-call spacing and 429 waits between the app and widgets. Timelines add entries at reset, one-hour stale, and seven-day expiry boundaries in the next 8 hours (`presentationDates`) and ask for the next one through `WidgetSchedule`: every 30 minutes while a live window is at 80% or more and resets within 12 hours, hourly otherwise, and hourly once that widget has reloaded 32 times in 24 hours, so even a busy day stays within about 40. iCloud and each key provider get at most 5 of the widget's 6 seconds (`TimeLimit`, `fetchWithinBudget`), hard limits that don't wait for a call that ignores cancellation; when iCloud doesn't answer in time, the previous cache's readings from other devices stay beside the fresh key readings. Countdowns use `ResetCountdown` (a ticking timer within a day). "Updated … ago" dates from the oldest shown reading's check (`ReadingCache.checkedAt`). `ReadingFreshness` ages each provider independently: stale after one hour, hidden after seven days. An elapsed reset shows "Reset · awaiting reading" with the retained measurement; it never synthesizes a live zero, forecast, or alert. `WidgetReloadLog` counts each widget's timeline builds (family and chosen provider); Settings › About shows the busiest widget's last 24 hours (aim: under 40). Accessory families say "Sample" for sample data, and a balance shows its amount rather than an empty gauge (circular and, on the Watch, corner and rectangular). Outside debug builds a sample cache ages like any other. Circular and corner complications open their provider; rectangular and inline ones open the list. The Smart Stack offers both the last 8 hours before the followed window resets and the next half day of the busiest window at 80% or more (`WidgetSchedule.relevance`).
- **History** (`UsageHistory`): 168 hourly used-% buckets, plus the hourly amount left for balances and the reset times, all optional in older records. Resets include ones used early (use falls sharply, to 10% or less, once the new window has begun). `HistoryStore` leaves out readings dated over an hour ahead, restarts a week that ran ahead of the clock, drops windows with no reading for a week, and moves Copilot's 2.0.0 `ai_credits` week to `premium_interactions`. Widgets queue the key readings they take (`history-pending/`, a file per provider and hour holding its latest reading, dropped after a week) for the app to record on its next refresh, the app being the one writer of `history.json`, and show them meanwhile (`HistoryStore.loadWithPending`). The app moves them aside (`history-taking/`) before recording them and deletes them once the week is saved, so one queued meanwhile, or a refresh cut short, loses nothing. `Forecast` turns history into "≈ N days left" (a rise under 1%, or under one whole unit, isn't a top-up) and a projected month, measured to the reading's check time and not once the month is over or the reading is a day old.

## iCloud environments

The container is `iCloud.app.tokenroom` (`TOKENROOM_CK_CONTAINER` in `Config/Base.xcconfig`), zone `Tokenroom`. Builds Xcode installs (development signing) use CloudKit's Development environment; TestFlight, the App Store, and the Developer ID Mac release use Production (`scripts/release.sh` refuses an export without it). Devices see each other only within one environment, so pair them deliberately: an Xcode-built Mac with an iPhone and Watch installed from Xcode, and the notarized Mac with TestFlight or App Store builds.

Development builds create record types and fields as they save them. Anything new has to be deployed to Production in CloudKit Console (the container's Schema › Deploy Schema Changes) before a Production build uses it; otherwise its saves fail there. The schema:

| Record type | Records | Fields |
|---|---|---|
| `Source` | one per collector, named by its source ID | `payload` (a `RelayEnvelope`), `kind`, `label`, `checkedAt`, `schema`, `appVersion` |
| `History` | `hist-<source>` | `payload`, `schema` |
| `Event` | one per alert, `evt-…` | `provider`, `level`, `title`, `body`, `resetsAt`, `alertKind`, `alertKey` (queryable: the alert subscription filters on it) |
| `Prefs` | `prefs-alerts` | `payload` |

New data goes inside a `payload` (versioned JSON) rather than into new fields where it can, so it needs no deployment: 2.0.1 added none. The iPhone saves two subscriptions: one on the zone (silent pushes) and one on `Event` creation (visible alerts).

## Alerts

`AlertRules` and `AlertLedger` (`Shared/Core/Alerts.swift`). IDs are deterministic (`evt-<provider>-<window>-<level>-<instance>`: the reset rounded to the hour for windows a day or longer, 10 minutes otherwise, and the day for windows with no reset), so any number of devices seeing one crossing leave one `Event`; the iPhone's `CKQuerySubscription` fires only on creation and filters on `alertKey IN subscribedKeys` (falling back to every event if the field isn't queryable yet). First sight and stale readings never alert. A reset time that moves while the window goes on (the old time still ahead, the move no more than a quarter of the window or 30 minutes, use not falling by 10 points) is the same window, and "fresh headroom" is only for resets in the last 12 hours. Money windows (usd, cny) raise `.lowBalance` instead of `.threshold`, at 80% and 95% whenever the balance switch is on, whatever the usage levels; a balance alert, named by the day (UTC), first checks for either neighbouring day's record under a day old (`wentOutOnANeighbouringDay`), so two devices either side of midnight don't both alert, whichever goes first (a real second crossing within a day, after a top-up, is quiet). `process` queues alerts in `pending`; `due` releases urgent ones at once and the rest after quiet hours; `markSent` only after delivery, so an alert iCloud didn't take is retried. A held alert goes out with its countdown as of then (`AlertRules.refreshed`), is dropped when its switch is turned off or the same window's higher level went out (`levelsSent`, even when the reset moved between them), and waits through quiet hours of any length. Quiet hours and choices are shared as `Prefs`; the iPhone applies quiet hours where it is now and gives the shared copy its zone when that changes, so a Mac holds alerts for the same night. Urgent alerts (95%, a run-out within the hour, a banked reset expiring within 6 hours) ignore quiet hours. Sessions (5-hour limits) take `sessionThresholds` and longer limits `thresholds` (`AlertPreferences.thresholds(for:)`; a saved copy without `sessionThresholds` gives sessions `thresholds`); both share the `threshold-<level>` key, so older Macs' alerts still come through, and the device that raises an alert applies the kind's own levels (older Macs apply `thresholds` to sessions until they update). `.runsOut` (`AlertRules.runsOut`, key `runsOut`, ID `evt-<provider>-<window>-runsOut-<instance>`) goes out once per window instance when its switch is on (`sessionRunsOut`, `limitRunsOut`), at least half is used, and the pace (a Mac's measured `RelayPace`; for the iPhone's own readings, its recent readings, `HistoryStore.samples`, passed to `AlertLedger.process(samples:)`; else the rate since the window began) runs out before the reset: at all for a session, a day early for a longer limit; never in the same reading as a threshold alert for that window, not past 95%, and a held one gives way to the window's 95% alert. Alerts carry the window's kind (`windowKind`) so a held one follows its kind's switches. Titles name limits with `RelayWindow.limitName` ("5-hour limit", "weekly limit"); windows show as `displayTitle` everywhere (a session is "5-hour"). The alert subscription sets no `collapseIDKey`: CloudKit would send it as every push's collapse ID. Macs send alerts; the iPhone notifies locally only for windows no Mac meters live (a reference set only on the iPhone makes that window its own), because iCloud doesn't notify the device that saved a record. Before notifying, the iPhone claims the alert (`CloudRelay.claimAlert`: creates the record only if no device has, keyed `UsageAlert.shownKey`, which no subscription lists). If a Mac's record is already there, its push already came and the iPhone stays quiet; another iPhone's (a `shown:` key) means nothing reached this one, so it shows the alert too. A Mac saving the same crossing later finds the record there and leaves it, which notifies nobody. Claims start once the alert subscription filters by kind. An alert shown while iCloud was away is claimed later (`unclaimedAlerts`, up to 18 hours). The ledger processes every provider the iPhone reads, so it stays current; only alerts for windows no Mac meters live (other iPhones don't count; Copilot's `ai_credits` from a Mac on 2.0.0 counts as `premium_interactions`) are shown here, the rest stay pending. The subscription falls back to every event only when CloudKit rejects the `alertKey` predicate (`invalidArguments`, `serverRejectedRequest`); other failures are retried on the next refresh. Add fields to `AlertPreferences` with a default in its lenient `init(from:)`.

## Live Activity

`SessionActivityAttributes` follows one window: a session, or a window at 80%+, resetting within 8 hours (`RelayProvider.windowToFollow`). Started from the first row of Close to a limit, a tile's context menu, the detail screen (`FollowButton`), `FollowUsageIntent` (Shortcuts, Siri via `TokenroomShortcuts`, Action button), or the Control. The app updates it on each rebuild (a refresh waits for that), alerting at 80% and 95% when those alerts are on for its kind of limit (95% only during quiet hours), and once (`ContentState.warnedRunsOut`) with the run-out alert's title and body when `AlertRules.runsOut` fires for its window, not in the same update as a level and, unless urgent, not during quiet hours; its meter carries the pace tick from `windowSeconds`; `staleDate` is the reset; it ends once the reset has passed, even without a newer reading, stale activities included. A stale activity shows as reset rather than at its last percentage and doesn't count as followed; following again ends it, and one still lingering after it ended, before starting the new one (`start` is async, so an intent doesn't return first, and runs on the main actor, checking again just before it starts one, so two Follows at once start one). A reset time the provider moves, with the window going on, updates it rather than ending it, even when the move is seen after the old time. Follow in Close to a limit follows the window its row shows when it resets within 8 hours. `.supplementalActivityFamilies([.small])` puts it in the Watch Smart Stack.

## iPhone without a Mac

Spec: `docs/iphone-login-without-a-mac.md`. `PhoneConnect` (Shared/APIKeys, pure) decides each provider: `readsWithKey` first (`.addKey`, Copilot's token included, whatever a Mac shows), then a live `.mac` source (`.fromMac`, blocks only a phone login), then the allowlist (`.signIn`), else `.needsMac(reason:)`. `PhoneConnect.productionAllowlist` is empty; tests pass their own set. Never use `isUnofficial` there. `CollectorKind` (Shared/Core: `mac`, `thisPhone`, `otherPhone`) rides on `RelayMerge.Source.kind`, `ReadingCache.Item.origin` (optional; `resolvedOrigin` falls back to the label for old caches), and `MobileStore.Reading.origin`; phrases "On this iPhone", "From your other iPhone", "From your Mac", and on the Watch "From your iPhone"/"From your Mac". `PhoneSessionStore`/`PhoneSessionClient`/`PhoneSessionRefresher` (Shared/APIKeys, excluded from the widget target by a membership exception) are built but have no production caller: the access group is the app id from `TokenroomApplicationIdentifier` (`PhoneSessionAvailability`, fails closed), `canReplace` before any POST, `exchanging` before the request, a failed write retried as a write, `markRejected` touches one item. The connect screen (`ConnectView`, `SettingsRoute.connect`, `tokenroom://connect`) and its copy sit behind `connectOnIPhone` in `UserDefaults.standard` (default off; `-connectOnIPhone YES` in any build). While it's on, the Watch context carries `connectAvailable: true` beside `readings` (`WatchHandoff`), and the Watch's empty state offers "Set up on iPhone", sending `[open: connect]` only while the iPhone app is reachable.

## News stays current

Opening News checks feeds older than `NewsFetcher.openInterval` (15 minutes); while the tab (or the Mac's News window, via `QuotaStore.newsBecameVisible`/`newsHidden`) is on screen, `NewsStore.keepCurrent` checks again every `liveInterval` (15 minutes) without notifying, so nobody has to pull or press Check Now. What arrives during a visit stays marked New for it and moves `seenAt`, so it doesn't come back as a badge.

## Meters and details

`MeterTrack` is a Canvas: rounded track, fill coloured by the usage gradient across the whole track, the even pace as a notch cut through the bar with a slim marker, and light stripes over the stretch past the pace when use runs ahead. `UsageRing` cuts the same notch. `UsageFacts` (Shared/Core) turns a window into Resets / Pace / Plan / Checked facts; `UsageFactsGrid` (Shared/UI) shows them on the iPhone detail's hero (ring, "N% left", facts) and in the Mac's expanded card. Settings rows on iPhone use `SettingsRowLabel` tiles and open with a `ReadingsStatusCard`; strings are unchanged.

## Checking UI without taps

Debug builds take launch arguments (they land in the standard defaults' argument domain):

- `-sampleMode YES -onboarded YES`: sample data, no onboarding.
- `-TokenroomOpen tokenroom://provider/claude` (or `news`, `settings`, `keys`): open a screen.
- `-TokenroomGallery home` or `lock`: every widget size and the Live Activity's Lock Screen view.
- `-TokenroomFollow claude`: start that provider's Live Activity.
- `-newsSection Today|Models|Announcements|Retiring`.
- Watch: `-sampleMode YES` and `-TokenroomOpen tokenroom://provider/claude`.

Build to a fixed DerivedData path so `simctl install` gets the fresh app, then `xcrun simctl launch <device> app.tokenroom.ios -sampleMode YES …` and `xcrun simctl io <device> screenshot`. Opening a URL with `simctl openurl` leaves an "Open in Tokenroom?" prompt; use `-TokenroomOpen` instead. Simulator screenshots don't show the Dynamic Island or Lock Screen, and `BGTaskScheduler` isn't available in the simulator.

## Copy and design

The Usage tab leads with Close to a limit (`CloseToLimitCard`: every live window at 80% or more, the limit reached, or ahead of pace with a run-out before its reset, most urgent first; Follow on the first row), then chips for banked resets and alerts that are off (news counts live on the News tab's badge). Then a tile per plan in a two-column `Grid`, one column at XXL and larger text sizes (`UsageTileView`, from `UsageTiles.tile`), in the order last ranked (`UsageTiles.ordered`: tiles re-rank when the tab appears, the app comes forward, or a pull to refresh finishes, not on background refreshes; a different set of readings ranks at once): the long window (weekly, a month, a billing cycle) as a `UsageRing` with the even-pace notch, the session as a solid `MeterTrack` with the pace tick, each saying when it resets or "Runs out …"; balances show their amount and forecast. Sessions are called "5-hour" (`UsageTiles.title`). A tile close to a limit gets a `usageTight` outline and a bell; a tile opens the provider's detail, and its context menu offers Follow. The News tab badges unseen items and marks them "New" for the visit (`beginVisit`/`endVisit` at tab-entry/window-opening boundaries, preserved through internal navigation). It opens on Today (`NewsEditions.today`: "Since you last looked" counts from `visitBaseline`, the newest followed model under two weeks old as the top story, up to eight more models, announcements grouped by tool with up to three headlines each, models retiring within 30 days), with filter chips for Models, Announcements (a River by day), and Retiring (`NewsFilter`, saved in `newsSection`). The pieces (`TopStoryView`, `ModelCardView`, `ToolNewsCard`, `RetiringModelRow`, `RiverRow`) live in `Shared/UI/NewsEditionViews.swift` for the Mac too. Headlines are set in the system serif, everything else in SF; links open in Safari, and `.multilineTextAlignment(.leading)` keeps link labels from centring. Feeds are read up to their size cap as they download (2 MB, and 4 MB for the ChatGPT & Codex changelog, whose items carry whole release notes); one cut short or broken shows what arrived, and its section says "Couldn't read …"; a failed check waits an hour. Titles fold into one row only within a product's own feeds (a changelog and its GitHub releases); across products only the same link does. The row kept notes the feed folded into it (`FeedItem.alsoIn`, set by `NewsCache.announcements`, never stored: "Also in Claude Code releases", or "Claude Code changelog" where the feed's name is the item's source). Feeds and labs added since a list was saved start on. The first check (turning News on) marks nothing new, items are dated no later than first seen, and links are web pages only. Providers show their own icons on every platform (on the Watch, inside each metered row's ring; `ProviderMark`: `Provider.assetName` in `Shared/UI/ProviderIcons.xcassets`; an official mark without its own square, `iconIsMark`, sits whole on a white tile with clear space, never cropped or recoloured). The monogram and tint stand in where there's no icon file (xAI API) and in widgets the system tints or renders clear (`widgetRenderingMode` other than full colour). Sources and each owner's terms are in `docs/provider-icons.md`; add an icon only from the owner's brand page or official GitHub, and never redraw one. Say "Tokenroom isn't affiliated with…" where a provider is named at length. Errors start with "Couldn't…". Links inside `List` and widgets tint their labels: set `.foregroundStyle(.primary)` on the `Link`.

App icons (a "T" of two usage meters, white on orange) are generated: `scripts/make-icons.py` writes `TokenroomMobile/AppIcon.icon` and `TokenroomWatch/AppIcon.icon` (a smaller T, so it clears the round mask). Change the script and rerun it; don't edit the `.icon` files by hand. Check a change in every look with Icon Composer's renderer: `ictool <file>.icon --export-image --output-file out.png --platform iOS --rendition Dark --width 512 --height 512 --scale 1` (renditions Default, Dark, TintedLight, TintedDark, ClearLight, ClearDark; platforms iOS, macOS, watchOS).

News caches store optional per-source success/failure times. New uncached follows fetch immediately, including a re-follow after an earlier uncached failure: `forcedSources` bypasses cooldown only for those feeds, and queued requests union their source IDs without losing a manual refresh. Transport and parsing failures otherwise retry after one hour independently of successful sources. Conditional GETs and byte limits remain. Manual refreshes during a pass coalesce into one follow-up. Today and Retiring show section health; empty states retain Follow, Show All, and Retry. Today's empty state uses the visible edition, so distant retirements cannot leave a blank page. Model lists use Show More, search covers titles/sources, prices label input/output per million tokens, and compact cards/specifications adapt to larger text. See `docs/settings-usage-news-validation.md` for implementation evidence and remaining runtime acceptance.

Provider ranking pairs the most urgent window's severity with that same window's percentage. `ReadingText.attention` explains an exhausted secondary limit before a pending reset in compact summaries. Rectangular widget fallbacks retain this explanation and stale counts; circular families show a dash and Reset with the full explanation in accessibility text. Watch summaries date only the readings still presented. Pass the timeline's presentation date into Watch/iPhone rows and details so unchanged data still updates time-dependent labels; amount-only tiles explain pending resets too. Keep test execution and runtime acceptance distinct from source review and compilation checks.

Watch membership comes from the newest cache envelope; older handovers may advance retained provider checks without undoing removals. `WatchCacheAccess` gates startup and all complication disk reads after sign-out/account changes, opening only after a validated cache write succeeds. Live Activities preserve measured usage at reset with optional `awaitingReading`, a dash and awaiting-reading caption, and no pace/stale threshold alert. Pinned widgets keep their chosen provider's unavailable state instead of substituting another provider. Queued News requests preserve any notification intent with OR and use the latest preferences.

A living Watch process must reconcile a newly validated complication cache on resume and after iCloud failure, even when normal refresh is throttled; `WatchCacheRecovery` follows the durable gate and `WatchStore` keeps a connection-error banner beside recovered data. Do not unlock phone handovers merely from an old disk file. `NewsStore` runs its feed pass in an unstructured store task so a cancelled page request does not discard the queued manual/follow pass. The Reset Soon relevance widget has no timeline callback; use one render date, best-effort Watch background reset scheduling, and widget reload on a crossed reset, while treating exact WidgetKit timing as device QA.
